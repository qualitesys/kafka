45   /**
46    * The administrative client for Kafka, which supports managing and inspecting topics, brokers, configurations and ACLs.
47    * <p>
48    * Instances returned from the {@code create} methods of this interface are guaranteed to be thread safe.
49    * However, the {@link KafkaFuture KafkaFutures} returned from request methods are executed
50    * by a single thread so it is important that any code which executes on that thread when they complete
51    * (using {@link KafkaFuture#thenApply(KafkaFuture.Function)}, for example) doesn't block
52    * for too long. If necessary, processing of results should be passed to another thread.
53    * <p>
54    * The operations exposed by Admin follow a consistent pattern:
55    * <ul>
56    *     <li>Admin instances should be created using {@link Admin#create(Properties)} or {@link Admin#create(Map)}</li>
57    *     <li>Each operation typically has two overloaded methods, one which uses a default set of options and an
58    *     overloaded method where the last parameter is an explicit options object.
59    *     <li>The operation method's first parameter is a {@code Collection} of items to perform
60    *     the operation on. Batching multiple requests into a single call is more efficient and should be
61    *     preferred over multiple calls to the same method.
62    *     <li>The operation methods execute asynchronously.
63    *     <li>Each {@code xxx} operation method returns an {@code XxxResult} class with methods which expose
64    *     {@link KafkaFuture} for accessing the result(s) of the operation.
65    *     <li>Typically an {@code all()} method is provided for getting the overall success/failure of the batch and a
66    *     {@code values()} method provided access to each item in a request batch.
67    *     Other methods may also be provided.
68    *     <li>For synchronous behaviour use {@link KafkaFuture#get()}
69    * </ul>
70    * <p>
71    * Here is a simple example of using an Admin client instance to create a new topic:
72    * <pre>
73    * {@code
74    * Properties props = new Properties();
75    * props.put(AdminClientConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
76    *
77    * try (Admin admin = Admin.create(props)) {
78    *   String topicName = "my-topic";
79    *   int partitions = 12;
80    *   short replicationFactor = 3;
81    *   // Create a compacted topic
82    *   CreateTopicsResult result = admin.createTopics(Collections.singleton(
83    *     new NewTopic(topicName, partitions, replicationFactor)
84    *       .configs(Collections.singletonMap(TopicConfig.CLEANUP_POLICY_CONFIG, TopicConfig.CLEANUP_POLICY_COMPACT))));
85    *
86    *   // Call values() to get the result for a specific topic
87    *   KafkaFuture<Void> future = result.values().get(topicName);
88    *
89    *   // Call get() to block until the topic creation is complete or has failed
90    *   // if creation failed the ExecutionException wraps the underlying cause.
91    *   future.get();
92    * }
93    * }
94    * </pre>
95    *
96    * <h3>Bootstrap and balancing</h3>
97    * <p>
98    * The {@code bootstrap.servers} config in the {@code Map} or {@code Properties} passed
99    * to {@link Admin#create(Properties)} is only used for discovering the brokers in the cluster,
100    * which the client will then connect to as needed.
101    * As such, it is sufficient to include only two or three broker addresses to cope with the possibility of brokers
102    * being unavailable.
103    * <p>
104    * Different operations necessitate requests being sent to different nodes in the cluster. For example
105    * {@link #createTopics(Collection)} communicates with the controller, but {@link #describeTopics(Collection)}
106    * can talk to any broker. When the recipient does not matter the instance will try to use the broker with the
107    * fewest outstanding requests.
108    * <p>
109    * The client will transparently retry certain errors which are usually transient.
110    * For example if the request for {@code createTopics()} get sent to a node which was not the controller
111    * the metadata would be refreshed and the request re-sent to the controller.
112    *
113    * <h3>Broker Compatibility</h3>
114    * <p>
115    * The minimum broker version required is 0.10.0.0. Methods with stricter requirements will specify the minimum broker
116    * version required.
117    * <p>
118    * This client was introduced in 0.11.0.0 and the API is still evolving. We will try to evolve the API in a compatible
119    * manner, but we reserve the right to make breaking changes in minor releases, if necessary. We will update the
120    * {@code InterfaceStability} annotation and this notice once the API is considered stable.
121    * <p>
122    */
123   @InterfaceStability.Evolving
