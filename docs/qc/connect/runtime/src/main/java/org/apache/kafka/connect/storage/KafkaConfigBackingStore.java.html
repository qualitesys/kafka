75   /**
76    * <p>
77    * Provides persistent storage of Kafka Connect connector configurations in a Kafka topic.
78    * </p>
79    * <p>
80    * This class manages both connector and task configurations. It tracks three types of configuration entries:
81    * <p/>
82    * 1. Connector config: map of string -> string configurations passed to the Connector class, with support for
83    * expanding this format if necessary. (Kafka key: connector-[connector-id]).
84    * These configs are *not* ephemeral. They represent the source of truth. If the entire Connect
85    * cluster goes down, this is all that is really needed to recover.
86    * 2. Task configs: map of string -> string configurations passed to the Task class, with support for expanding
87    * this format if necessary. (Kafka key: task-[connector-id]-[task-id]).
88    * These configs are ephemeral; they are stored here to a) disseminate them to all workers while
89    * ensuring agreement and b) to allow faster cluster/worker recovery since the common case
90    * of recovery (restoring a connector) will simply result in the same configuration as before
91    * the failure.
92    * 3. Task commit "configs": records indicating that previous task config entries should be committed and all task
93    * configs for a connector can be applied. (Kafka key: commit-[connector-id].
94    * This config has two effects. First, it records the number of tasks the connector is currently
95    * running (and can therefore increase/decrease parallelism). Second, because each task config
96    * is stored separately but they need to be applied together to ensure each partition is assigned
97    * to a single task, this record also indicates that task configs for the specified connector
98    * can be "applied" or "committed".
99    * </p>
100    * <p>
101    * This configuration is expected to be stored in a *single partition* and *compacted* topic. Using a single partition
102    * ensures we can enforce ordering on messages, allowing Kafka to be used as a write ahead log. Compaction allows
103    * us to clean up outdated configurations over time. However, this combination has some important implications for
104    * the implementation of this class and the configuration state that it may expose.
105    * </p>
106    * <p>
107    * Connector configurations are independent of all other configs, so they are handled easily. Writing a single record
108    * is already atomic, so these can be applied as soon as they are read. One connectors config does not affect any
109    * others, and they do not need to coordinate with the connector's task configuration at all.
110    * </p>
111    * <p>
112    * The most obvious implication for task configs is the need for the commit messages. Because Kafka does not
113    * currently have multi-record transactions or support atomic batch record writes, task commit messages are required
114    * to ensure that readers do not end up using inconsistent configs. For example, consider if a connector wrote configs
115    * for its tasks, then was reconfigured and only managed to write updated configs for half its tasks. If task configs
116    * were applied immediately you could be using half the old configs and half the new configs. In that condition, some
117    * partitions may be double-assigned because the old config and new config may use completely different assignments.
118    * Therefore, when reading the log, we must buffer config updates for a connector's tasks and only apply atomically them
119    * once a commit message has been read.
120    * </p>
121    * <p>
122    * However, there are also further challenges. This simple buffering approach would work fine as long as the entire log was
123    * always available, but we would like to be able to enable compaction so our configuration topic does not grow
124    * indefinitely. Compaction may break a normal log because old entries will suddenly go missing. A new worker reading
125    * from the beginning of the log in order to build up the full current configuration will see task commits, but some
126    * records required for those commits will have been removed because the same keys have subsequently been rewritten.
127    * For example, if you have a sequence of record keys [connector-foo-config, task-foo-1-config, task-foo-2-config,
128    * commit-foo (2 tasks), task-foo-1-config, commit-foo (1 task)], we can end up with a compacted log containing
129    * [connector-foo-config, task-foo-2-config, commit-foo (2 tasks), task-foo-1-config, commit-foo (1 task)]. When read
130    * back, the first commit will see an invalid state because the first task-foo-1-config has been cleaned up.
131    * </p>
132    * <p>
133    * Compaction can further complicate things if writing new task configs fails mid-write. Consider a similar scenario
134    * as the previous one, but in this case both the first and second update will write 2 task configs. However, the
135    * second write fails half of the way through:
136    * [connector-foo-config, task-foo-1-config, task-foo-2-config, commit-foo (2 tasks), task-foo-1-config]. Now compaction
137    * occurs and we're left with
138    * [connector-foo-config, task-foo-2-config, commit-foo (2 tasks), task-foo-1-config]. At the first commit, we don't
139    * have a complete set of configs. And because of the failure, there is no second commit. We are left in an inconsistent
140    * state with no obvious way to resolve the issue -- we can try to keep on reading, but the failed node may never
141    * recover and write the updated config. Meanwhile, other workers may have seen the entire log; they will see the second
142    * task-foo-1-config waiting to be applied, but will otherwise think everything is ok -- they have a valid set of task
143    * configs for connector "foo".
144    * </p>
145    * <p>
146    * Because we can encounter these inconsistencies and addressing them requires support from the rest of the system
147    * (resolving the task configuration inconsistencies requires support from the connector instance to regenerate updated
148    * configs), this class exposes not only the current set of configs, but also which connectors have inconsistent data.
149    * This allows users of this class (i.e., Herder implementations) to take action to resolve any inconsistencies. These
150    * inconsistencies should be rare (as described above, due to compaction combined with leader failures in the middle
151    * of updating task configurations).
152    * </p>
153    * <p>
154    * Note that the expectation is that this config storage system has only a single writer at a time.
155    * The caller (Herder) must ensure this is the case. In distributed mode this will require forwarding config change
156    * requests to the leader in the cluster (i.e. the worker group coordinated by the Kafka broker).
157    * </p>
158    * <p>
159    * Since processing of the config log occurs in a background thread, callers must take care when using accessors.
160    * To simplify handling this correctly, this class only exposes a mechanism to snapshot the current state of the cluster.
161    * Updates may continue to be applied (and callbacks invoked) in the background. Callers must take care that they are
162    * using a consistent snapshot and only update when it is safe. In particular, if task configs are updated which require
163    * synchronization across workers to commit offsets and update the configuration, callbacks and updates during the
164    * rebalance must be deferred.
165    * </p>
166    */

325       @Override
326       public void start() {
327           log.info("Starting KafkaConfigBackingStore");

329           // updates can continue to occur in the background

514        * and the write fails
515        */
516       @Override
517       public void putTaskConfigs(String connector, List<Map<String, String>> configs) {
518           // Make sure we're at the end of the log. We should be the only writer, but we want to make sure we don't have
519           // any outstanding lagging data to consume.
520           try {
521               configLog.readToEnd().get(READ_TO_END_TIMEOUT_MS, TimeUnit.MILLISECONDS);
522           } catch (InterruptedException | ExecutionException | TimeoutException e) {
523               log.error("Failed to write root configuration to Kafka: ", e);
524               throw new ConnectException("Error writing root configuration to Kafka", e);
525           }
526   
527           int taskCount = configs.size();
528   
529           // Start sending all the individual updates
530           int index = 0;
531           for (Map<String, String> taskConfig: configs) {
532               Struct connectConfig = new Struct(TASK_CONFIGURATION_V0);
533               connectConfig.put("properties", taskConfig);
534               byte[] serializedConfig = converter.fromConnectData(topic, TASK_CONFIGURATION_V0, connectConfig);
535               log.debug("Writing configuration for connector '{}' task {}", connector, index);
536               ConnectorTaskId connectorTaskId = new ConnectorTaskId(connector, index);
537               sendPrivileged(TASK_KEY(connectorTaskId), serializedConfig);
538               index++;
539           }
540   
541           // Finally, send the commit to update the number of tasks and apply the new configs, then wait until we read to
542           // the end of the log
543           try {
544               // Read to end to ensure all the task configs have been written
545               if (taskCount > 0) {
546                   configLog.readToEnd().get(READ_TO_END_TIMEOUT_MS, TimeUnit.MILLISECONDS);
547               }
548               // Write the commit message
549               Struct connectConfig = new Struct(CONNECTOR_TASKS_COMMIT_V0);
550               connectConfig.put("tasks", taskCount);
551               byte[] serializedConfig = converter.fromConnectData(topic, CONNECTOR_TASKS_COMMIT_V0, connectConfig);
552               log.debug("Writing commit for connector '{}' with {} tasks.", connector, taskCount);
553               sendPrivileged(COMMIT_TASKS_KEY(connector), serializedConfig);
554   
555               // Read to end to ensure all the commit messages have been written
556               configLog.readToEnd().get(READ_TO_END_TIMEOUT_MS, TimeUnit.MILLISECONDS);
557           } catch (InterruptedException | ExecutionException | TimeoutException e) {
558               log.error("Failed to write root configuration to Kafka: ", e);
559               throw new ConnectException("Error writing root configuration to Kafka", e);
560           }
561       }

751       private class ConsumeCallback implements Callback<ConsumerRecord<String, byte[]>> {
752           @Override
753           public void onCompletion(Throwable error, ConsumerRecord<String, byte[]> record) {
754               if (error != null) {
755                   log.error("Unexpected in consumer callback for KafkaConfigBackingStore: ", error);
756                   return;
757               }
758   
759               final SchemaAndValue value;
760               try {
761                   value = converter.toConnectData(topic, record.value());
762               } catch (DataException e) {
763                   log.error("Failed to convert config data to Kafka Connect format: ", e);
764                   return;
765               }
766               // Make the recorded offset match the API used for positions in the consumer -- return the offset of the
767               // *next record*, not the last one consumed.
768               offset = record.offset() + 1;

771                   String connectorName = record.key().substring(TARGET_STATE_PREFIX.length());

773               } else if (record.key().startsWith(CONNECTOR_PREFIX)) {
774                   String connectorName = record.key().substring(CONNECTOR_PREFIX.length());
775                   processConnectorConfigRecord(connectorName, value);
776               } else if (record.key().startsWith(TASK_PREFIX)) {

790                       updateListener.onRestartRequest(request);
791                   }
792               } else if (record.key().startsWith(TASK_COUNT_RECORD_PREFIX)) {
793                   String connectorName = record.key().substring(TASK_COUNT_RECORD_PREFIX.length());

795               } else if (record.key().equals(SESSION_KEY_KEY)) {
796                   processSessionKeyRecord(value);
797               } else {
798                   log.error("Discarding config update record with invalid key: {}", record.key());
799               }
800           }

915       private void processTasksCommitRecord(String connectorName, SchemaAndValue value) {
916           List<ConnectorTaskId> updatedTasks = new ArrayList<>();
917           synchronized (lock) {
918               // Apply any outstanding deferred task updates for the given connector. Note that just because we
919               // encounter a commit message does not mean it will result in consistent output. In particular due to
920               // compaction, there may be cases where . For example if we have the following sequence of writes:
921               //
922               // 1. Write connector "foo"'s config
923               // 2. Write connector "foo", task 1's config <-- compacted
924               // 3. Write connector "foo", task 2's config
925               // 4. Write connector "foo" task commit message
926               // 5. Write connector "foo", task 1's config
927               // 6. Write connector "foo", task 2's config
928               // 7. Write connector "foo" task commit message
929               //
930               // then when a new worker starts up, if message 2 had been compacted, then when message 4 is applied
931               // "foo" will not have a complete set of configs. Only when message 7 is applied will the complete
932               // configuration be available. Worse, if the leader died while writing messages 5, 6, and 7 such that
933               // only 5 was written, then there may be nothing that will finish writing the configs and get the
934               // log back into a consistent state.
935               //
936               // It is expected that the user of this class (i.e., the Herder) will take the necessary action to
937               // resolve this (i.e., get the connector to recommit its configuration). This inconsistent state is
938               // exposed in the snapshots provided via ClusterConfigState so they are easy to handle.
939               if (!(value.value() instanceof Map)) { // Schema-less, so we get maps instead of structs
940                   log.error("Ignoring connector tasks configuration commit for connector '{}' because it is in the wrong format: {}", connectorName, className(value.value()));
941                   return;
942               }
943               Map<ConnectorTaskId, Map<String, String>> deferred = deferredTaskUpdates.get(connectorName);
944   
945               @SuppressWarnings("unchecked")
946               int newTaskCount = intValue(((Map<String, Object>) value.value()).get("tasks"));
947   
948               // Validate the configs we're supposed to update to ensure we're getting a complete configuration
949               // update of all tasks that are expected based on the number of tasks in the commit message.
950               Set<Integer> taskIdSet = taskIds(connectorName, deferred);
951               if (!completeTaskIdSet(taskIdSet, newTaskCount)) {
952                   // Given the logic for writing commit messages, we should only hit this condition due to compacted
953                   // historical data, in which case we would not have applied any updates yet and there will be no
954                   // task config data already committed for the connector, so we shouldn't have to clear any data
955                   // out. All we need to do is add the flag marking it inconsistent.
956                   log.debug("We have an incomplete set of task configs for connector '{}' probably due to compaction. So we are not doing anything with the new configuration.", connectorName);
957                   inconsistent.add(connectorName);
958               } else {
959                   if (deferred != null) {
960                       taskConfigs.putAll(deferred);
961                       updatedTasks.addAll(deferred.keySet());
962                       connectorTaskConfigGenerations.compute(connectorName, (ignored, generation) -> generation != null ? generation + 1 : 0);
963                   }
964                   inconsistent.remove(connectorName);
965               }
966               // Always clear the deferred entries, even if we didn't apply them. If they represented an inconsistent
967               // update, then we need to see a completely fresh set of configs after this commit message, so we don't
968               // want any of these outdated configs
969               if (deferred != null)
970                   deferred.clear();
971   
972               connectorTaskCounts.put(connectorName, newTaskCount);
973           }
974   
975           // If task configs appear after the latest task count record, the connector needs a new round of zombie fencing
976           // before it can start tasks with these configs
977           connectorsPendingFencing.add(connectorName);
978           if (started)
979               updateListener.onTaskConfigUpdate(updatedTasks);
980       }
