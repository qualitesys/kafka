123   /**
124    * This class makes it easier to write tests to verify the behavior of topologies created with {@link Topology} or
125    * {@link StreamsBuilder}.
126    * You can test simple topologies that have a single processor, or very complex topologies that have multiple sources,
127    * processors, sinks, or sub-topologies.
128    * Best of all, the class works without a real Kafka broker, so the tests execute very quickly with very little overhead.
129    * <p>
130    * Using the {@code TopologyTestDriver} in tests is easy: simply instantiate the driver and provide a {@link Topology}
131    * (cf. {@link StreamsBuilder#build()}) and {@link Properties config}, {@link #createInputTopic(String, Serializer, Serializer) create}
132    * and use a {@link TestInputTopic} to supply an input records to the topology,
133    * and then {@link #createOutputTopic(String, Deserializer, Deserializer) create} and use a {@link TestOutputTopic} to read and
134    * verify any output records by the topology.
135    * <p>
136    * Although the driver doesn't use a real Kafka broker, it does simulate Kafka {@link Consumer consumers} and
137    * {@link Producer producers} that read and write raw {@code byte[]} messages.
138    * You can let {@link TestInputTopic} and {@link TestOutputTopic} to handle conversion
139    * form regular Java objects to raw bytes.
140    *
141    * <h2>Driver setup</h2>
142    * In order to create a {@code TopologyTestDriver} instance, you need a {@link Topology} and a {@link Properties config}.
143    * The configuration needs to be representative of what you'd supply to the real topology, so that means including
144    * several key properties (cf. {@link StreamsConfig}).
145    * For example, the following code fragment creates a configuration that specifies a timestamp extractor,
146    * default serializers and deserializers for string keys and values:
147    *
148    * <pre>{@code
149    * Properties props = new Properties();
150    * props.setProperty(StreamsConfig.DEFAULT_TIMESTAMP_EXTRACTOR_CLASS_CONFIG, CustomTimestampExtractor.class.getName());
151    * props.setProperty(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.String().getClass().getName());
152    * props.setProperty(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.String().getClass().getName());
153    * Topology topology = ...
154    * TopologyTestDriver driver = new TopologyTestDriver(topology, props);
155    * }</pre>
156    *
157    * <p> Note that the {@code TopologyTestDriver} processes input records synchronously.
158    * This implies that {@link StreamsConfig#COMMIT_INTERVAL_MS_CONFIG commit.interval.ms} and
159    * {@link StreamsConfig#STATESTORE_CACHE_MAX_BYTES_CONFIG cache.max.bytes.buffering} configuration have no effect.
160    * The driver behaves as if both configs would be set to zero, i.e., as if a "commit" (and thus "flush") would happen
161    * after each input record.
162    *
163    * <h2>Processing messages</h2>
164    * <p>
165    * Your test can supply new input records on any of the topics that the topology's sources consume.
166    * This test driver simulates single-partitioned input topics.
167    * Here's an example of an input message on the topic named {@code input-topic}:
168    *
169    * <pre>{@code
170    * TestInputTopic<String, String> inputTopic = driver.createInputTopic("input-topic", stringSerdeSerializer, stringSerializer);
171    * inputTopic.pipeInput("key1", "value1");
172    * }</pre>
173    *
174    * When {@link TestInputTopic#pipeInput(Object, Object)} is called, the driver passes the input message through to the appropriate source that
175    * consumes the named topic, and will invoke the processor(s) downstream of the source.
176    * If your topology's processors forward messages to sinks, your test can then consume these output messages to verify
177    * they match the expected outcome.
178    * For example, if our topology should have generated 2 messages on {@code output-topic-1} and 1 message on
179    * {@code output-topic-2}, then our test can obtain these messages using the
180    * {@link TestOutputTopic#readKeyValue()}  method:
181    *
182    * <pre>{@code
183    * TestOutputTopic<String, String> outputTopic1 = driver.createOutputTopic("output-topic-1", stringDeserializer, stringDeserializer);
184    * TestOutputTopic<String, String> outputTopic2 = driver.createOutputTopic("output-topic-2", stringDeserializer, stringDeserializer);
185    *
186    * KeyValue<String, String> record1 = outputTopic1.readKeyValue();
187    * KeyValue<String, String> record2 = outputTopic2.readKeyValue();
188    * KeyValue<String, String> record3 = outputTopic1.readKeyValue();
189    * }</pre>
190    *
191    * Again, our example topology generates messages with string keys and values, so we supply our string deserializer
192    * instance for use on both the keys and values. Your test logic can then verify whether these output records are
193    * correct.
194    * <p>
195    * Note, that calling {@code pipeInput()} will also trigger {@link PunctuationType#STREAM_TIME event-time} base
196    * {@link ProcessorContext#schedule(Duration, PunctuationType, Punctuator) punctuation} callbacks.
197    * However, you won't trigger {@link PunctuationType#WALL_CLOCK_TIME wall-clock} type punctuations that you must
198    * trigger manually via {@link #advanceWallClockTime(Duration)}.
199    * <p>
200    * Finally, when completed, make sure your tests {@link #close()} the driver to release all resources and
201    * {@link org.apache.kafka.streams.processor.api.Processor processors}.
202    *
203    * <h2>Processor state</h2>
204    * <p>
205    * Some processors use Kafka {@link StateStore state storage}, so this driver class provides the generic
206    * {@link #getStateStore(String)} as well as store-type specific methods so that your tests can check the underlying
207    * state store(s) used by your topology's processors.
208    * In our previous example, after we supplied a single input message and checked the three output messages, our test
209    * could also check the key value store to verify the processor correctly added, removed, or updated internal state.
210    * Or, our test might have pre-populated some state <em>before</em> submitting the input message, and verified afterward
211    * that the processor(s) correctly updated the state.
212    *
213    * @see TestInputTopic
214    * @see TestOutputTopic
215    */

589       private void completeAllProcessableWork() {
590           // for internally triggered processing (like wall-clock punctuations),
591           // we might have buffered some records to internal topics that need to
592           // be piped back in to kick-start the processing loop. This is idempotent
593           // and therefore harmless in the case where all we've done is enqueued an
594           // input record from the user.
595           captureOutputsAndReEnqueueInternalResults();
596   
597           // If the topology only has global tasks, then `task` would be null.
598           // For this method, it just means there's nothing to do.
599           if (task != null) {
600               while (task.hasRecordsQueued() && task.isProcessable(mockWallClockTime.milliseconds())) {
601                   // Process the record ...
602                   task.process(mockWallClockTime.milliseconds());
603                   task.maybePunctuateStreamTime();
604                   commit(task.prepareCommit());
605                   task.postCommit(true);
606                   captureOutputsAndReEnqueueInternalResults();
607               }
608               if (task.hasRecordsQueued()) {
609                   log.info("Due to the {} configuration, there are currently some records" +
610                                " that cannot be processed. Advancing wall-clock time or" +
611                                " enqueuing records on the empty topics will allow" +
612                                " Streams to process more.",
613                            StreamsConfig.MAX_TASK_IDLE_MS_CONFIG);
614               }
615           }
616       }
