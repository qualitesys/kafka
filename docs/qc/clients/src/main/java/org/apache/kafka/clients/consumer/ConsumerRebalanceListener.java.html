19   import java.time.Duration;
20   import java.util.Collection;
21   
22   import org.apache.kafka.common.TopicPartition;

24   /**
25    * A callback interface that the user can implement to trigger custom actions when the set of partitions assigned to the
26    * consumer changes.
27    * <p>
28    * This is applicable when the consumer is having Kafka auto-manage group membership. If the consumer directly assigns partitions,
29    * those partitions will never be reassigned and this callback is not applicable.
30    * <p>
31    * When Kafka is managing the group membership, a partition re-assignment will be triggered any time the members of the group change or the subscription
32    * of the members changes. This can occur when processes die, new process instances are added or old instances come back to life after failure.
33    * Partition re-assignments can also be triggered by changes affecting the subscribed topics (e.g. when the number of partitions is
34    * administratively adjusted).
35    * <p>
36    * There are many uses for this functionality. One common use is saving offsets in a custom store. By saving offsets in
37    * the {@link #onPartitionsRevoked(Collection)} call we can ensure that any time partition assignment changes
38    * the offset gets saved.
39    * <p>
40    * Another use is flushing out any kind of cache of intermediate results the consumer may be keeping. For example,
41    * consider a case where the consumer is subscribed to a topic containing user page views, and the goal is to count the
42    * number of page views per user for each five minute window. Let's say the topic is partitioned by the user id so that
43    * all events for a particular user go to a single consumer instance. The consumer can keep in memory a running
44    * tally of actions per user and only flush these out to a remote data store when its cache gets too big. However if a
45    * partition is reassigned it may want to automatically trigger a flush of this cache, before the new owner takes over
46    * consumption.
47    * <p>
48    * This callback will only execute in the user thread as part of the {@link Consumer#poll(java.time.Duration) poll(long)} call
49    * whenever partition assignment changes.
50    * <p>
51    * Under normal conditions, if a partition is reassigned from one consumer to another, then the old consumer will
52    * always invoke {@link #onPartitionsRevoked(Collection) onPartitionsRevoked} for that partition prior to the new consumer
53    * invoking {@link #onPartitionsAssigned(Collection) onPartitionsAssigned} for the same partition. So if offsets or other state is saved in the
54    * {@link #onPartitionsRevoked(Collection) onPartitionsRevoked} call by one consumer member, it will be always accessible by the time the
55    * other consumer member taking over that partition and triggering its {@link #onPartitionsAssigned(Collection) onPartitionsAssigned} callback to load the state.
56    * <p>
57    * You can think of revocation as a graceful way to give up ownership of a partition. In some cases, the consumer may not have an opportunity to do so.
58    * For example, if the session times out, then the partitions may be reassigned before we have a chance to revoke them gracefully.
59    * For this case, we have a third callback {@link #onPartitionsLost(Collection)}. The difference between this function and
60    * {@link #onPartitionsRevoked(Collection)} is that upon invocation of {@link #onPartitionsLost(Collection)}, the partitions
61    * may already be owned by some other members in the group and therefore users would not be able to commit its consumed offsets for example.
62    * Users could implement these two functions differently (by default,
63    * {@link #onPartitionsLost(Collection)} will be calling {@link #onPartitionsRevoked(Collection)} directly); for example, in the
64    * {@link #onPartitionsLost(Collection)} we should not need to store the offsets since we know these partitions are no longer owned by the consumer
65    * at that time.
66    * <p>
67    * During a rebalance event, the {@link #onPartitionsAssigned(Collection) onPartitionsAssigned} function will always be triggered exactly once when
68    * the rebalance completes. That is, even if there is no newly assigned partitions for a consumer member, its {@link #onPartitionsAssigned(Collection) onPartitionsAssigned}
69    * will still be triggered with an empty collection of partitions. As a result this function can be used also to notify when a rebalance event has happened.
70    * With eager rebalancing, {@link #onPartitionsRevoked(Collection)} will always be called at the start of a rebalance. On the other hand, {@link #onPartitionsLost(Collection)}
71    * will only be called when there were non-empty partitions that were lost.
72    * With cooperative rebalancing, {@link #onPartitionsRevoked(Collection)} and {@link #onPartitionsLost(Collection)}
73    * will only be triggered when there are non-empty partitions revoked or lost from this consumer member during a rebalance event.
74    * <p>
75    * It is possible
76    * for a {@link org.apache.kafka.common.errors.WakeupException} or {@link org.apache.kafka.common.errors.InterruptException}
77    * to be raised from one of these nested invocations. In this case, the exception will be propagated to the current
78    * invocation of {@link KafkaConsumer#poll(java.time.Duration)} in which this callback is being executed. This means it is not
79    * necessary to catch these exceptions and re-attempt to wakeup or interrupt the consumer thread.
80    * Also if the callback function implementation itself throws an exception, this exception will be propagated to the current
81    * invocation of {@link KafkaConsumer#poll(java.time.Duration)} as well.
82    * <p>
83    * Note that callbacks only serve as notification of an assignment change.
84    * They cannot be used to express acceptance of the change.
85    * Hence throwing an exception from a callback does not affect the assignment in any way,
86    * as it will be propagated all the way up to the {@link KafkaConsumer#poll(java.time.Duration)} call.
87    * If user captures the exception in the caller, the callback is still assumed successful and no further retries will be attempted.
88    * <p>
89    *
90    * Here is pseudo-code for a callback implementation for saving offsets:
91    * <pre>
92    * {@code
93    *   public class SaveOffsetsOnRebalance implements ConsumerRebalanceListener {
94    *       private Consumer<?,?> consumer;
95    *
96    *       public SaveOffsetsOnRebalance(Consumer<?,?> consumer) {
97    *           this.consumer = consumer;
98    *       }
99    *
100    *       public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
101    *           // save the offsets in an external store using some custom code not described here
102    *           for(TopicPartition partition: partitions)
103    *              saveOffsetInExternalStore(consumer.position(partition));
104    *       }
105    *
106    *       public void onPartitionsLost(Collection<TopicPartition> partitions) {
107    *           // do not need to save the offsets since these partitions are probably owned by other consumers already
108    *       }
109    *
110    *       public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
111    *           // read the offsets from an external store using some custom code not described here
112    *           for(TopicPartition partition: partitions)
113    *              consumer.seek(partition, readOffsetFromExternalStore(partition));
114    *       }
115    *   }
116    * }
117    * </pre>
118    */
119   public interface ConsumerRebalanceListener {
120   
121       /**
122        * A callback method the user can implement to provide handling of offset commits to a customized store.
123        * This method will be called during a rebalance operation when the consumer has to give up some partitions.
124        * It can also be called when consumer is being closed ({@link KafkaConsumer#close(Duration)})
125        * or is unsubscribing ({@link KafkaConsumer#unsubscribe()}).
126        * It is recommended that offsets should be committed in this callback to either Kafka or a
127        * custom offset store to prevent duplicate data.
128        * <p>
129        * In eager rebalancing, it will always be called at the start of a rebalance and after the consumer stops fetching data.
130        * In cooperative rebalancing, it will be called at the end of a rebalance on the set of partitions being revoked iff the set is non-empty.
131        * For examples on usage of this API, see Usage Examples section of {@link KafkaConsumer KafkaConsumer}.
132        * <p>
133        * It is common for the revocation callback to use the consumer instance in order to commit offsets. It is possible
134        * for a {@link org.apache.kafka.common.errors.WakeupException} or {@link org.apache.kafka.common.errors.InterruptException}
135        * to be raised from one of these nested invocations. In this case, the exception will be propagated to the current
136        * invocation of {@link KafkaConsumer#poll(java.time.Duration)} in which this callback is being executed. This means it is not
137        * necessary to catch these exceptions and re-attempt to wakeup or interrupt the consumer thread.
138        *
139        * @param partitions The list of partitions that were assigned to the consumer and now need to be revoked (may not
140        *                   include all currently assigned partitions, i.e. there may still be some partitions left)
141        * @throws org.apache.kafka.common.errors.WakeupException If raised from a nested call to {@link KafkaConsumer}
142        * @throws org.apache.kafka.common.errors.InterruptException If raised from a nested call to {@link KafkaConsumer}
143        */
144       void onPartitionsRevoked(Collection<TopicPartition> partitions);
145   
146       /**
147        * A callback method the user can implement to provide handling of customized offsets on completion of a successful
148        * partition re-assignment. This method will be called after the partition re-assignment completes and before the
149        * consumer starts fetching data, and only as the result of a {@link Consumer#poll(java.time.Duration) poll(long)} call.
150        * <p>
151        * It is guaranteed that under normal conditions all the processes in a consumer group will execute their
152        * {@link #onPartitionsRevoked(Collection)} callback before any instance executes its
153        * {@link #onPartitionsAssigned(Collection)} callback. During exceptional scenarios, partitions may be migrated
154        * without the old owner being notified (i.e. their {@link #onPartitionsRevoked(Collection)} callback not triggered),
155        * and later when the old owner consumer realized this event, the {@link #onPartitionsLost(Collection)} (Collection)} callback
156        * will be triggered by the consumer then.
157        * <p>
158        * It is common for the assignment callback to use the consumer instance in order to query offsets. It is possible
159        * for a {@link org.apache.kafka.common.errors.WakeupException} or {@link org.apache.kafka.common.errors.InterruptException}
160        * to be raised from one of these nested invocations. In this case, the exception will be propagated to the current
161        * invocation of {@link KafkaConsumer#poll(java.time.Duration)} in which this callback is being executed. This means it is not
162        * necessary to catch these exceptions and re-attempt to wakeup or interrupt the consumer thread.
163        *
164        * @param partitions The list of partitions that are now assigned to the consumer (previously owned partitions will
165        *                   NOT be included, i.e. this list will only include newly added partitions)
166        * @throws org.apache.kafka.common.errors.WakeupException If raised from a nested call to {@link KafkaConsumer}
167        * @throws org.apache.kafka.common.errors.InterruptException If raised from a nested call to {@link KafkaConsumer}
168        */
169       void onPartitionsAssigned(Collection<TopicPartition> partitions);
170   
171       /**
172        * A callback method you can implement to provide handling of cleaning up resources for partitions that have already
173        * been reassigned to other consumers. This method will not be called during normal execution as the owned partitions would
174        * first be revoked by calling the {@link ConsumerRebalanceListener#onPartitionsRevoked}, before being reassigned
175        * to other consumers during a rebalance event. However, during exceptional scenarios when the consumer realized that it
176        * does not own this partition any longer, i.e. not revoked via a normal rebalance event, then this method would be invoked.
177        * <p>
178        * For example, this function is called if a consumer's session timeout has expired, or if a fatal error has been
179        * received indicating the consumer is no longer part of the group.
180        * <p>
181        * By default it will just trigger {@link ConsumerRebalanceListener#onPartitionsRevoked}; for users who want to distinguish
182        * the handling logic of revoked partitions v.s. lost partitions, they can override the default implementation.
183        * <p>
184        * It is possible
185        * for a {@link org.apache.kafka.common.errors.WakeupException} or {@link org.apache.kafka.common.errors.InterruptException}
186        * to be raised from one of these nested invocations. In this case, the exception will be propagated to the current
187        * invocation of {@link KafkaConsumer#poll(java.time.Duration)} in which this callback is being executed. This means it is not
188        * necessary to catch these exceptions and re-attempt to wakeup or interrupt the consumer thread.
189        *
190        * @param partitions The list of partitions that were assigned to the consumer and now have been reassigned
191        *                   to other consumers. With the current protocol this will always include all of the consumer's
192        *                   previously assigned partitions, but this may change in future protocols (ie there would still
193        *                   be some partitions left)
194        * @throws org.apache.kafka.common.errors.WakeupException If raised from a nested call to {@link KafkaConsumer}
195        * @throws org.apache.kafka.common.errors.InterruptException If raised from a nested call to {@link KafkaConsumer}
196        */
197       default void onPartitionsLost(Collection<TopicPartition> partitions) {
198           onPartitionsRevoked(partitions);
199       }
200   }
