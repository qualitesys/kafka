92   /**
93    * A Kafka client that publishes records to the Kafka cluster.
94    * <P>
95    * The producer is <i>thread safe</i> and sharing a single producer instance across threads will generally be faster than
96    * having multiple instances.
97    * <p>
98    * Here is a simple example of using the producer to send records with strings containing sequential numbers as the key/value
99    * pairs.
100    * <pre>
101    * {@code
102    * Properties props = new Properties();
103    * props.put("bootstrap.servers", "localhost:9092");
104    * props.put("linger.ms", 1);
105    * props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
106    * props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
107    *
108    * Producer<String, String> producer = new KafkaProducer<>(props);
109    * for (int i = 0; i < 100; i++)
110    *     producer.send(new ProducerRecord<String, String>("my-topic", Integer.toString(i), Integer.toString(i)));
111    *
112    * producer.close();
113    * }</pre>
114    * <p>
115    * The producer consists of a pool of buffer space that holds records that haven't yet been transmitted to the server
116    * as well as a background I/O thread that is responsible for turning these records into requests and transmitting them
117    * to the cluster. Failure to close the producer after use will leak these resources.
118    * <p>
119    * The {@link #send(ProducerRecord) send()} method is asynchronous. When called, it adds the record to a buffer of pending record sends
120    * and immediately returns. This allows the producer to batch together individual records for efficiency.
121    * <p>
122    * The <code>acks</code> config controls the criteria under which requests are considered complete. The default setting "all"
123    * will result in blocking on the full commit of the record, the slowest but most durable setting.
124    * <p>
125    * If the request fails, the producer can automatically retry. The <code>retries</code> setting defaults to <code>Integer.MAX_VALUE</code>, and
126    * it's recommended to use <code>delivery.timeout.ms</code> to control retry behavior, instead of <code>retries</code>.
127    * <p>
128    * The producer maintains buffers of unsent records for each partition. These buffers are of a size specified by
129    * the <code>batch.size</code> config. Making this larger can result in more batching, but requires more memory (since we will
130    * generally have one of these buffers for each active partition).
131    * <p>
132    * By default a buffer is available to send immediately even if there is additional unused space in the buffer. However if you
133    * want to reduce the number of requests you can set <code>linger.ms</code> to something greater than 0. This will
134    * instruct the producer to wait up to that number of milliseconds before sending a request in hope that more records will
135    * arrive to fill up the same batch. This is analogous to Nagle's algorithm in TCP. For example, in the code snippet above,
136    * likely all 100 records would be sent in a single request since we set our linger time to 1 millisecond. However this setting
137    * would add 1 millisecond of latency to our request waiting for more records to arrive if we didn't fill up the buffer. Note that
138    * records that arrive close together in time will generally batch together even with <code>linger.ms=0</code>. So, under heavy load,
139    * batching will occur regardless of the linger configuration; however setting this to something larger than 0 can lead to fewer, more
140    * efficient requests when not under maximal load at the cost of a small amount of latency.
141    * <p>
142    * The <code>buffer.memory</code> controls the total amount of memory available to the producer for buffering. If records
143    * are sent faster than they can be transmitted to the server then this buffer space will be exhausted. When the buffer space is
144    * exhausted additional send calls will block. The threshold for time to block is determined by <code>max.block.ms</code> after which it throws
145    * a TimeoutException.
146    * <p>
147    * The <code>key.serializer</code> and <code>value.serializer</code> instruct how to turn the key and value objects the user provides with
148    * their <code>ProducerRecord</code> into bytes. You can use the included {@link org.apache.kafka.common.serialization.ByteArraySerializer} or
149    * {@link org.apache.kafka.common.serialization.StringSerializer} for simple string or byte types.
150    * <p>
151    * From Kafka 0.11, the KafkaProducer supports two additional modes: the idempotent producer and the transactional producer.
152    * The idempotent producer strengthens Kafka's delivery semantics from at least once to exactly once delivery. In particular
153    * producer retries will no longer introduce duplicates. The transactional producer allows an application to send messages
154    * to multiple partitions (and topics!) atomically.
155    * </p>
156    * <p>
157    * From Kafka 3.0, the <code>enable.idempotence</code> configuration defaults to true. When enabling idempotence,
158    * <code>retries</code> config will default to <code>Integer.MAX_VALUE</code> and the <code>acks</code> config will
159    * default to <code>all</code>. There are no API changes for the idempotent producer, so existing applications will
160    * not need to be modified to take advantage of this feature.
161    * </p>
162    * <p>
163    * To take advantage of the idempotent producer, it is imperative to avoid application level re-sends since these cannot
164    * be de-duplicated. As such, if an application enables idempotence, it is recommended to leave the <code>retries</code>
165    * config unset, as it will be defaulted to <code>Integer.MAX_VALUE</code>. Additionally, if a {@link #send(ProducerRecord)}
166    * returns an error even with infinite retries (for instance if the message expires in the buffer before being sent),
167    * then it is recommended to shut down the producer and check the contents of the last produced message to ensure that
168    * it is not duplicated. Finally, the producer can only guarantee idempotence for messages sent within a single session.
169    * </p>
170    * <p>To use the transactional producer and the attendant APIs, you must set the <code>transactional.id</code>
171    * configuration property. If the <code>transactional.id</code> is set, idempotence is automatically enabled along with
172    * the producer configs which idempotence depends on. Further, topics which are included in transactions should be configured
173    * for durability. In particular, the <code>replication.factor</code> should be at least <code>3</code>, and the
174    * <code>min.insync.replicas</code> for these topics should be set to 2. Finally, in order for transactional guarantees
175    * to be realized from end-to-end, the consumers must be configured to read only committed messages as well.
176    * </p>
177    * <p>
178    * The purpose of the <code>transactional.id</code> is to enable transaction recovery across multiple sessions of a
179    * single producer instance. It would typically be derived from the shard identifier in a partitioned, stateful, application.
180    * As such, it should be unique to each producer instance running within a partitioned application.
181    * </p>
182    * <p>All the new transactional APIs are blocking and will throw exceptions on failure. The example
183    * below illustrates how the new APIs are meant to be used. It is similar to the example above, except that all
184    * 100 messages are part of a single transaction.
185    * </p>
186    * <p>
187    * <pre>
188    * {@code
189    * Properties props = new Properties();
190    * props.put("bootstrap.servers", "localhost:9092");
191    * props.put("transactional.id", "my-transactional-id");
192    * Producer<String, String> producer = new KafkaProducer<>(props, new StringSerializer(), new StringSerializer());
193    *
194    * producer.initTransactions();
195    *
196    * try {
197    *     producer.beginTransaction();
198    *     for (int i = 0; i < 100; i++)
199    *         producer.send(new ProducerRecord<>("my-topic", Integer.toString(i), Integer.toString(i)));
200    *     producer.commitTransaction();
201    * } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException e) {
202    *     // We can't recover from these exceptions, so our only option is to close the producer and exit.
203    *     producer.close();
204    * } catch (KafkaException e) {
205    *     // For all other exceptions, just abort the transaction and try again.
206    *     producer.abortTransaction();
207    * }
208    * producer.close();
209    * } </pre>
210    * </p>
211    * <p>
212    * As is hinted at in the example, there can be only one open transaction per producer. All messages sent between the
213    * {@link #beginTransaction()} and {@link #commitTransaction()} calls will be part of a single transaction. When the
214    * <code>transactional.id</code> is specified, all messages sent by the producer must be part of a transaction.
215    * </p>
216    * <p>
217    * The transactional producer uses exceptions to communicate error states. In particular, it is not required
218    * to specify callbacks for <code>producer.send()</code> or to call <code>.get()</code> on the returned Future: a
219    * <code>KafkaException</code> would be thrown if any of the
220    * <code>producer.send()</code> or transactional calls hit an irrecoverable error during a transaction. See the {@link #send(ProducerRecord)}
221    * documentation for more details about detecting errors from a transactional send.
222    * </p>
223    * </p>By calling
224    * <code>producer.abortTransaction()</code> upon receiving a <code>KafkaException</code> we can ensure that any
225    * successful writes are marked as aborted, hence keeping the transactional guarantees.
226    * </p>
227    * <p>
228    * This client can communicate with brokers that are version 0.10.0 or newer. Older or newer brokers may not support
229    * certain client features.  For instance, the transactional APIs need broker versions 0.11.0 or later. You will receive an
230    * <code>UnsupportedVersionException</code> when invoking an API that is not available in the running broker version.
231    * </p>
232    */

607       /**

609        *
610        * This method does the following:
611        *   1. Ensures any transactions initiated by previous instances of the producer with the same
612        *      transactional.id are completed. If the previous instance had failed with a transaction in
613        *      progress, it will be aborted. If the last transaction had begun completion,
614        *      but not yet finished, this method awaits its completion.
615        *   2. Gets the internal producer id and epoch, used in all future transactional
616        *      messages issued by the producer.
617        *
618        * Note that this method will raise {@link TimeoutException} if the transactional state cannot
619        * be initialized before expiration of {@code max.block.ms}. Additionally, it will raise {@link InterruptException}
620        * if interrupted. It is safe to retry in either case, but once the transactional state has been successfully
621        * initialized, this method should no longer be used.
622        *
623        * @throws IllegalStateException if no transactional.id has been configured
624        * @throws org.apache.kafka.common.errors.UnsupportedVersionException fatal error indicating the broker
625        *         does not support transactions (i.e. if its version is lower than 0.11.0.0)
626        * @throws org.apache.kafka.common.errors.AuthorizationException fatal error indicating that the configured
627        *         transactional.id is not authorized. See the exception for more details
628        * @throws KafkaException if the producer has encountered a previous fatal error or for any other unexpected error
629        * @throws TimeoutException if the time taken for initialize the transaction has surpassed <code>max.block.ms</code>.
630        * @throws InterruptException if the thread is interrupted while blocked

637           sender.wakeup();
