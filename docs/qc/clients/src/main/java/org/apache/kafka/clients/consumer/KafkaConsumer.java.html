85   /**
86    * A client that consumes records from a Kafka cluster.
87    * <p>
88    * This client transparently handles the failure of Kafka brokers, and transparently adapts as topic partitions
89    * it fetches migrate within the cluster. This client also interacts with the broker to allow groups of
90    * consumers to load balance consumption using <a href="#consumergroups">consumer groups</a>.
91    * <p>
92    * The consumer maintains TCP connections to the necessary brokers to fetch data.
93    * Failure to close the consumer after use will leak these connections.
94    * The consumer is not thread-safe. See <a href="#multithreaded">Multi-threaded Processing</a> for more details.
95    *
96    * <h3>Cross-Version Compatibility</h3>
97    * This client can communicate with brokers that are version 0.10.0 or newer. Older or newer brokers may not support
98    * certain features. For example, 0.10.0 brokers do not support offsetsForTimes, because this feature was added
99    * in version 0.10.1. You will receive an {@link org.apache.kafka.common.errors.UnsupportedVersionException}
100    * when invoking an API that is not available on the running broker version.
101    * <p>
102    *
103    * <h3>Offsets and Consumer Position</h3>
104    * Kafka maintains a numerical offset for each record in a partition. This offset acts as a unique identifier of
105    * a record within that partition, and also denotes the position of the consumer in the partition. For example, a consumer
106    * which is at position 5 has consumed records with offsets 0 through 4 and will next receive the record with offset 5. There
107    * are actually two notions of position relevant to the user of the consumer:
108    * <p>
109    * The {@link #position(TopicPartition) position} of the consumer gives the offset of the next record that will be given
110    * out. It will be one larger than the highest offset the consumer has seen in that partition. It automatically advances
111    * every time the consumer receives messages in a call to {@link #poll(Duration)}.
112    * <p>
113    * The {@link #commitSync() committed position} is the last offset that has been stored securely. Should the
114    * process fail and restart, this is the offset that the consumer will recover to. The consumer can either automatically commit
115    * offsets periodically; or it can choose to control this committed position manually by calling one of the commit APIs
116    * (e.g. {@link #commitSync() commitSync} and {@link #commitAsync(OffsetCommitCallback) commitAsync}).
117    * <p>
118    * This distinction gives the consumer control over when a record is considered consumed. It is discussed in further
119    * detail below.
120    *
121    * <h3><a name="consumergroups">Consumer Groups and Topic Subscriptions</a></h3>
122    *
123    * Kafka uses the concept of <i>consumer groups</i> to allow a pool of processes to divide the work of consuming and
124    * processing records. These processes can either be running on the same machine or they can be
125    * distributed over many machines to provide scalability and fault tolerance for processing. All consumer instances
126    * sharing the same {@code group.id} will be part of the same consumer group.
127    * <p>
128    * Each consumer in a group can dynamically set the list of topics it wants to subscribe to through one of the
129    * {@link #subscribe(Collection, ConsumerRebalanceListener) subscribe} APIs. Kafka will deliver each message in the
130    * subscribed topics to one process in each consumer group. This is achieved by balancing the partitions between all
131    * members in the consumer group so that each partition is assigned to exactly one consumer in the group. So if there
132    * is a topic with four partitions, and a consumer group with two processes, each process would consume from two partitions.
133    * <p>
134    * Membership in a consumer group is maintained dynamically: if a process fails, the partitions assigned to it will
135    * be reassigned to other consumers in the same group. Similarly, if a new consumer joins the group, partitions will be moved
136    * from existing consumers to the new one. This is known as <i>rebalancing</i> the group and is discussed in more
137    * detail <a href="#failuredetection">below</a>. Group rebalancing is also used when new partitions are added
138    * to one of the subscribed topics or when a new topic matching a {@link #subscribe(Pattern, ConsumerRebalanceListener) subscribed regex}
139    * is created. The group will automatically detect the new partitions through periodic metadata refreshes and
140    * assign them to members of the group.
141    * <p>
142    * Conceptually you can think of a consumer group as being a single logical subscriber that happens to be made up of
143    * multiple processes. As a multi-subscriber system, Kafka naturally supports having any number of consumer groups for a
144    * given topic without duplicating data (additional consumers are actually quite cheap).
145    * <p>
146    * This is a slight generalization of the functionality that is common in messaging systems. To get semantics similar to
147    * a queue in a traditional messaging system all processes would be part of a single consumer group and hence record
148    * delivery would be balanced over the group like with a queue. Unlike a traditional messaging system, though, you can
149    * have multiple such groups. To get semantics similar to pub-sub in a traditional messaging system each process would
150    * have its own consumer group, so each process would subscribe to all the records published to the topic.
151    * <p>
152    * In addition, when group reassignment happens automatically, consumers can be notified through a {@link ConsumerRebalanceListener},
153    * which allows them to finish necessary application-level logic such as state cleanup, manual offset
154    * commits, etc. See <a href="#rebalancecallback">Storing Offsets Outside Kafka</a> for more details.
155    * <p>
156    * It is also possible for the consumer to <a href="#manualassignment">manually assign</a> specific partitions
157    * (similar to the older "simple" consumer) using {@link #assign(Collection)}. In this case, dynamic partition
158    * assignment and consumer group coordination will be disabled.
159    *
160    * <h3><a name="failuredetection">Detecting Consumer Failures</a></h3>
161    *
162    * After subscribing to a set of topics, the consumer will automatically join the group when {@link #poll(Duration)} is
163    * invoked. The poll API is designed to ensure consumer liveness. As long as you continue to call poll, the consumer
164    * will stay in the group and continue to receive messages from the partitions it was assigned. Underneath the covers,
165    * the consumer sends periodic heartbeats to the server. If the consumer crashes or is unable to send heartbeats for
166    * a duration of {@code session.timeout.ms}, then the consumer will be considered dead and its partitions will
167    * be reassigned.
168    * <p>
169    * It is also possible that the consumer could encounter a "livelock" situation where it is continuing
170    * to send heartbeats, but no progress is being made. To prevent the consumer from holding onto its partitions
171    * indefinitely in this case, we provide a liveness detection mechanism using the {@code max.poll.interval.ms}
172    * setting. Basically if you don't call poll at least as frequently as the configured max interval,
173    * then the client will proactively leave the group so that another consumer can take over its partitions. When this happens,
174    * you may see an offset commit failure (as indicated by a {@link CommitFailedException} thrown from a call to {@link #commitSync()}).
175    * This is a safety mechanism which guarantees that only active members of the group are able to commit offsets.
176    * So to stay in the group, you must continue to call poll.
177    * <p>
178    * The consumer provides two configuration settings to control the behavior of the poll loop:
179    * <ol>
180    *     <li><code>max.poll.interval.ms</code>: By increasing the interval between expected polls, you can give
181    *     the consumer more time to handle a batch of records returned from {@link #poll(Duration)}. The drawback
182    *     is that increasing this value may delay a group rebalance since the consumer will only join the rebalance
183    *     inside the call to poll. You can use this setting to bound the time to finish a rebalance, but
184    *     you risk slower progress if the consumer cannot actually call {@link #poll(Duration) poll} often enough.</li>
185    *     <li><code>max.poll.records</code>: Use this setting to limit the total records returned from a single
186    *     call to poll. This can make it easier to predict the maximum that must be handled within each poll
187    *     interval. By tuning this value, you may be able to reduce the poll interval, which will reduce the
188    *     impact of group rebalancing.</li>
189    * </ol>
190    * <p>
191    * For use cases where message processing time varies unpredictably, neither of these options may be sufficient.
192    * The recommended way to handle these cases is to move message processing to another thread, which allows
193    * the consumer to continue calling {@link #poll(Duration) poll} while the processor is still working.
194    * Some care must be taken to ensure that committed offsets do not get ahead of the actual position.
195    * Typically, you must disable automatic commits and manually commit processed offsets for records only after the
196    * thread has finished handling them (depending on the delivery semantics you need).
197    * Note also that you will need to {@link #pause(Collection) pause} the partition so that no new records are received
198    * from poll until after thread has finished handling those previously returned.

200    * <h3>Usage Examples</h3>
201    * The consumer APIs offer flexibility to cover a variety of consumption use cases. Here are some examples to
202    * demonstrate how to use them.
203    *
204    * <h4>Automatic Offset Committing</h4>
205    * This example demonstrates a simple usage of Kafka's consumer api that relies on automatic offset committing.
206    * <p>
207    * <pre>
208    *     Properties props = new Properties();
209    *     props.setProperty(&quot;bootstrap.servers&quot;, &quot;localhost:9092&quot;);
210    *     props.setProperty(&quot;group.id&quot;, &quot;test&quot;);
211    *     props.setProperty(&quot;enable.auto.commit&quot;, &quot;true&quot;);
212    *     props.setProperty(&quot;auto.commit.interval.ms&quot;, &quot;1000&quot;);
213    *     props.setProperty(&quot;key.deserializer&quot;, &quot;org.apache.kafka.common.serialization.StringDeserializer&quot;);
214    *     props.setProperty(&quot;value.deserializer&quot;, &quot;org.apache.kafka.common.serialization.StringDeserializer&quot;);
215    *     KafkaConsumer&lt;String, String&gt; consumer = new KafkaConsumer&lt;&gt;(props);
216    *     consumer.subscribe(Arrays.asList(&quot;foo&quot;, &quot;bar&quot;));
217    *     while (true) {
218    *         ConsumerRecords&lt;String, String&gt; records = consumer.poll(Duration.ofMillis(100));
219    *         for (ConsumerRecord&lt;String, String&gt; record : records)
220    *             System.out.printf(&quot;offset = %d, key = %s, value = %s%n&quot;, record.offset(), record.key(), record.value());
221    *     }
222    * </pre>
223    *
224    * The connection to the cluster is bootstrapped by specifying a list of one or more brokers to contact using the
225    * configuration {@code bootstrap.servers}. This list is just used to discover the rest of the brokers in the
226    * cluster and need not be an exhaustive list of servers in the cluster (though you may want to specify more than one in
227    * case there are servers down when the client is connecting).
228    * <p>
229    * Setting {@code enable.auto.commit} means that offsets are committed automatically with a frequency controlled by
230    * the config {@code auto.commit.interval.ms}.
231    * <p>
232    * In this example the consumer is subscribing to the topics <i>foo</i> and <i>bar</i> as part of a group of consumers
233    * called <i>test</i> as configured with {@code group.id}.
234    * <p>
235    * The deserializer settings specify how to turn bytes into objects. For example, by specifying string deserializers, we
236    * are saying that our record's key and value will just be simple strings.
237    *
238    * <h4>Manual Offset Control</h4>
239    *
240    * Instead of relying on the consumer to periodically commit consumed offsets, users can also control when records
241    * should be considered as consumed and hence commit their offsets. This is useful when the consumption of the messages
242    * is coupled with some processing logic and hence a message should not be considered as consumed until it is completed processing.
243   
244    * <p>
245    * <pre>
246    *     Properties props = new Properties();
247    *     props.setProperty(&quot;bootstrap.servers&quot;, &quot;localhost:9092&quot;);
248    *     props.setProperty(&quot;group.id&quot;, &quot;test&quot;);
249    *     props.setProperty(&quot;enable.auto.commit&quot;, &quot;false&quot;);
250    *     props.setProperty(&quot;key.deserializer&quot;, &quot;org.apache.kafka.common.serialization.StringDeserializer&quot;);
251    *     props.setProperty(&quot;value.deserializer&quot;, &quot;org.apache.kafka.common.serialization.StringDeserializer&quot;);
252    *     KafkaConsumer&lt;String, String&gt; consumer = new KafkaConsumer&lt;&gt;(props);
253    *     consumer.subscribe(Arrays.asList(&quot;foo&quot;, &quot;bar&quot;));
254    *     final int minBatchSize = 200;
255    *     List&lt;ConsumerRecord&lt;String, String&gt;&gt; buffer = new ArrayList&lt;&gt;();
256    *     while (true) {
257    *         ConsumerRecords&lt;String, String&gt; records = consumer.poll(Duration.ofMillis(100));
258    *         for (ConsumerRecord&lt;String, String&gt; record : records) {
259    *             buffer.add(record);
260    *         }
261    *         if (buffer.size() &gt;= minBatchSize) {
262    *             insertIntoDb(buffer);
263    *             consumer.commitSync();
264    *             buffer.clear();
265    *         }
266    *     }
267    * </pre>
268    *
269    * In this example we will consume a batch of records and batch them up in memory. When we have enough records
270    * batched, we will insert them into a database. If we allowed offsets to auto commit as in the previous example, records
271    * would be considered consumed after they were returned to the user in {@link #poll(Duration) poll}. It would then be
272    * possible
273    * for our process to fail after batching the records, but before they had been inserted into the database.
274    * <p>
275    * To avoid this, we will manually commit the offsets only after the corresponding records have been inserted into the
276    * database. This gives us exact control of when a record is considered consumed. This raises the opposite possibility:
277    * the process could fail in the interval after the insert into the database but before the commit (even though this
278    * would likely just be a few milliseconds, it is a possibility). In this case the process that took over consumption
279    * would consume from last committed offset and would repeat the insert of the last batch of data. Used in this way
280    * Kafka provides what is often called "at-least-once" delivery guarantees, as each record will likely be delivered one
281    * time but in failure cases could be duplicated.
282    * <p>
283    * <b>Note: Using automatic offset commits can also give you "at-least-once" delivery, but the requirement is that
284    * you must consume all data returned from each call to {@link #poll(Duration)} before any subsequent calls, or before
285    * {@link #close() closing} the consumer. If you fail to do either of these, it is possible for the committed offset
286    * to get ahead of the consumed position, which results in missing records. The advantage of using manual offset
287    * control is that you have direct control over when a record is considered "consumed."</b>
288    * <p>
289    * The above example uses {@link #commitSync() commitSync} to mark all received records as committed. In some cases
290    * you may wish to have even finer control over which records have been committed by specifying an offset explicitly.
291    * In the example below we commit offset after we finish handling the records in each partition.
292    * <p>
293    * <pre>
294    *     try {
295    *         while(running) {
296    *             ConsumerRecords&lt;String, String&gt; records = consumer.poll(Duration.ofMillis(Long.MAX_VALUE));
297    *             for (TopicPartition partition : records.partitions()) {
298    *                 List&lt;ConsumerRecord&lt;String, String&gt;&gt; partitionRecords = records.records(partition);
299    *                 for (ConsumerRecord&lt;String, String&gt; record : partitionRecords) {
300    *                     System.out.println(record.offset() + &quot;: &quot; + record.value());
301    *                 }
302    *                 long lastOffset = partitionRecords.get(partitionRecords.size() - 1).offset();
303    *                 consumer.commitSync(Collections.singletonMap(partition, new OffsetAndMetadata(lastOffset + 1)));
304    *             }
305    *         }
306    *     } finally {
307    *       consumer.close();
308    *     }
309    * </pre>
310    *
311    * <b>Note: The committed offset should always be the offset of the next message that your application will read.</b>
312    * Thus, when calling {@link #commitSync(Map) commitSync(offsets)} you should add one to the offset of the last message processed.
313    *
314    * <h4><a name="manualassignment">Manual Partition Assignment</a></h4>
315    *
316    * In the previous examples, we subscribed to the topics we were interested in and let Kafka dynamically assign a
317    * fair share of the partitions for those topics based on the active consumers in the group. However, in
318    * some cases you may need finer control over the specific partitions that are assigned. For example:
319    * <p>
320    * <ul>
321    * <li>If the process is maintaining some kind of local state associated with that partition (like a
322    * local on-disk key-value store), then it should only get records for the partition it is maintaining on disk.
323    * <li>If the process itself is highly available and will be restarted if it fails (perhaps using a
324    * cluster management framework like YARN, Mesos, or AWS facilities, or as part of a stream processing framework). In
325    * this case there is no need for Kafka to detect the failure and reassign the partition since the consuming process
326    * will be restarted on another machine.
327    * </ul>
328    * <p>
329    * To use this mode, instead of subscribing to the topic using {@link #subscribe(Collection) subscribe}, you just call
330    * {@link #assign(Collection)} with the full list of partitions that you want to consume.
331    *
332    * <pre>
333    *     String topic = &quot;foo&quot;;
334    *     TopicPartition partition0 = new TopicPartition(topic, 0);
335    *     TopicPartition partition1 = new TopicPartition(topic, 1);
336    *     consumer.assign(Arrays.asList(partition0, partition1));
337    * </pre>
338    *
339    * Once assigned, you can call {@link #poll(Duration) poll} in a loop, just as in the preceding examples to consume
340    * records. The group that the consumer specifies is still used for committing offsets, but now the set of partitions
341    * will only change with another call to {@link #assign(Collection) assign}. Manual partition assignment does
342    * not use group coordination, so consumer failures will not cause assigned partitions to be rebalanced. Each consumer
343    * acts independently even if it shares a groupId with another consumer. To avoid offset commit conflicts, you should
344    * usually ensure that the groupId is unique for each consumer instance.
345    * <p>
346    * Note that it isn't possible to mix manual partition assignment (i.e. using {@link #assign(Collection) assign})
347    * with dynamic partition assignment through topic subscription (i.e. using {@link #subscribe(Collection) subscribe}).
348    *
349    * <h4><a name="rebalancecallback">Storing Offsets Outside Kafka</h4>
350    *
351    * The consumer application need not use Kafka's built-in offset storage, it can store offsets in a store of its own
352    * choosing. The primary use case for this is allowing the application to store both the offset and the results of the
353    * consumption in the same system in a way that both the results and offsets are stored atomically. This is not always
354    * possible, but when it is it will make the consumption fully atomic and give "exactly once" semantics that are
355    * stronger than the default "at-least once" semantics you get with Kafka's offset commit functionality.
356    * <p>
357    * Here are a couple of examples of this type of usage:
358    * <ul>
359    * <li>If the results of the consumption are being stored in a relational database, storing the offset in the database
360    * as well can allow committing both the results and offset in a single transaction. Thus either the transaction will
361    * succeed and the offset will be updated based on what was consumed or the result will not be stored and the offset
362    * won't be updated.
363    * <li>If the results are being stored in a local store it may be possible to store the offset there as well. For
364    * example a search index could be built by subscribing to a particular partition and storing both the offset and the
365    * indexed data together. If this is done in a way that is atomic, it is often possible to have it be the case that even
366    * if a crash occurs that causes unsync'd data to be lost, whatever is left has the corresponding offset stored as well.
367    * This means that in this case the indexing process that comes back having lost recent updates just resumes indexing
368    * from what it has ensuring that no updates are lost.
369    * </ul>
370    * <p>
371    * Each record comes with its own offset, so to manage your own offset you just need to do the following:
372    *
373    * <ul>
374    * <li>Configure <code>enable.auto.commit=false</code>
375    * <li>Use the offset provided with each {@link ConsumerRecord} to save your position.
376    * <li>On restart restore the position of the consumer using {@link #seek(TopicPartition, long)}.
377    * </ul>
378    *
379    * <p>
380    * This type of usage is simplest when the partition assignment is also done manually (this would be likely in the
381    * search index use case described above). If the partition assignment is done automatically special care is
382    * needed to handle the case where partition assignments change. This can be done by providing a
383    * {@link ConsumerRebalanceListener} instance in the call to {@link #subscribe(Collection, ConsumerRebalanceListener)}
384    * and {@link #subscribe(Pattern, ConsumerRebalanceListener)}.
385    * For example, when partitions are taken from a consumer the consumer will want to commit its offset for those partitions by
386    * implementing {@link ConsumerRebalanceListener#onPartitionsRevoked(Collection)}. When partitions are assigned to a
387    * consumer, the consumer will want to look up the offset for those new partitions and correctly initialize the consumer
388    * to that position by implementing {@link ConsumerRebalanceListener#onPartitionsAssigned(Collection)}.
389    * <p>
390    * Another common use for {@link ConsumerRebalanceListener} is to flush any caches the application maintains for
391    * partitions that are moved elsewhere.
392    *
393    * <h4>Controlling The Consumer's Position</h4>
394    *
395    * In most use cases the consumer will simply consume records from beginning to end, periodically committing its
396    * position (either automatically or manually). However Kafka allows the consumer to manually control its position,
397    * moving forward or backwards in a partition at will. This means a consumer can re-consume older records, or skip to
398    * the most recent records without actually consuming the intermediate records.
399    * <p>
400    * There are several instances where manually controlling the consumer's position can be useful.
401    * <p>
402    * One case is for time-sensitive record processing it may make sense for a consumer that falls far enough behind to not
403    * attempt to catch up processing all records, but rather just skip to the most recent records.
404    * <p>
405    * Another use case is for a system that maintains local state as described in the previous section. In such a system
406    * the consumer will want to initialize its position on start-up to whatever is contained in the local store. Likewise
407    * if the local state is destroyed (say because the disk is lost) the state may be recreated on a new machine by
408    * re-consuming all the data and recreating the state (assuming that Kafka is retaining sufficient history).
409    * <p>
410    * Kafka allows specifying the position using {@link #seek(TopicPartition, long)} to specify the new position. Special
411    * methods for seeking to the earliest and latest offset the server maintains are also available (
412    * {@link #seekToBeginning(Collection)} and {@link #seekToEnd(Collection)} respectively).
413    *
414    * <h4>Consumption Flow Control</h4>
415    *
416    * If a consumer is assigned multiple partitions to fetch data from, it will try to consume from all of them at the same time,
417    * effectively giving these partitions the same priority for consumption. However in some cases consumers may want to
418    * first focus on fetching from some subset of the assigned partitions at full speed, and only start fetching other partitions
419    * when these partitions have few or no data to consume.
420    *
421    * <p>
422    * One of such cases is stream processing, where processor fetches from two topics and performs the join on these two streams.
423    * When one of the topics is long lagging behind the other, the processor would like to pause fetching from the ahead topic
424    * in order to get the lagging stream to catch up. Another example is bootstraping upon consumer starting up where there are
425    * a lot of history data to catch up, the applications usually want to get the latest data on some of the topics before consider
426    * fetching other topics.
427    *
428    * <p>
429    * Kafka supports dynamic controlling of consumption flows by using {@link #pause(Collection)} and {@link #resume(Collection)}
430    * to pause the consumption on the specified assigned partitions and resume the consumption
431    * on the specified paused partitions respectively in the future {@link #poll(Duration)} calls.
432    *
433    * <h3>Reading Transactional Messages</h3>
434    *
435    * <p>
436    * Transactions were introduced in Kafka 0.11.0 wherein applications can write to multiple topics and partitions atomically.
437    * In order for this to work, consumers reading from these partitions should be configured to only read committed data.
438    * This can be achieved by setting the {@code isolation.level=read_committed} in the consumer's configuration.
439    *
440    * <p>
441    * In <code>read_committed</code> mode, the consumer will read only those transactional messages which have been
442    * successfully committed. It will continue to read non-transactional messages as before. There is no client-side
443    * buffering in <code>read_committed</code> mode. Instead, the end offset of a partition for a <code>read_committed</code>
444    * consumer would be the offset of the first message in the partition belonging to an open transaction. This offset
445    * is known as the 'Last Stable Offset'(LSO).</p>
446    *
447    * <p>
448    * A {@code read_committed} consumer will only read up to the LSO and filter out any transactional
449    * messages which have been aborted. The LSO also affects the behavior of {@link #seekToEnd(Collection)} and
450    * {@link #endOffsets(Collection)} for {@code read_committed} consumers, details of which are in each method's documentation.
451    * Finally, the fetch lag metrics are also adjusted to be relative to the LSO for {@code read_committed} consumers.
452    *
453    * <p>
454    * Partitions with transactional messages will include commit or abort markers which indicate the result of a transaction.
455    * There markers are not returned to applications, yet have an offset in the log. As a result, applications reading from
456    * topics with transactional messages will see gaps in the consumed offsets. These missing messages would be the transaction
457    * markers, and they are filtered out for consumers in both isolation levels. Additionally, applications using
458    * {@code read_committed} consumers may also see gaps due to aborted transactions, since those messages would not
459    * be returned by the consumer and yet would have valid offsets.
460    *
461    * <h3><a name="multithreaded">Multi-threaded Processing</a></h3>
462    *
463    * The Kafka consumer is NOT thread-safe. All network I/O happens in the thread of the application
464    * making the call. It is the responsibility of the user to ensure that multi-threaded access
465    * is properly synchronized. Un-synchronized access will result in {@link ConcurrentModificationException}.
466    *
467    * <p>
468    * The only exception to this rule is {@link #wakeup()}, which can safely be used from an external thread to
469    * interrupt an active operation. In this case, a {@link org.apache.kafka.common.errors.WakeupException} will be
470    * thrown from the thread blocking on the operation. This can be used to shutdown the consumer from another thread.
471    * The following snippet shows the typical pattern:
472    *
473    * <pre>
474    * public class KafkaConsumerRunner implements Runnable {
475    *     private final AtomicBoolean closed = new AtomicBoolean(false);
476    *     private final KafkaConsumer consumer;
477    *
478    *     public KafkaConsumerRunner(KafkaConsumer consumer) {
479    *       this.consumer = consumer;
480    *     }
481    *
482    *     {@literal}@Override
483    *     public void run() {
484    *         try {
485    *             consumer.subscribe(Arrays.asList("topic"));
486    *             while (!closed.get()) {
487    *                 ConsumerRecords records = consumer.poll(Duration.ofMillis(10000));
488    *                 // Handle new records
489    *             }
490    *         } catch (WakeupException e) {
491    *             // Ignore exception if closing
492    *             if (!closed.get()) throw e;
493    *         } finally {
494    *             consumer.close();
495    *         }
496    *     }
497    *
498    *     // Shutdown hook which can be called from a separate thread
499    *     public void shutdown() {
500    *         closed.set(true);
501    *         consumer.wakeup();
502    *     }
503    * }
504    * </pre>
505    *
506    * Then in a separate thread, the consumer can be shutdown by setting the closed flag and waking up the consumer.
507    *
508    * <p>
509    * <pre>
510    *     closed.set(true);
511    *     consumer.wakeup();
512    * </pre>
513    *
514    * <p>
515    * Note that while it is possible to use thread interrupts instead of {@link #wakeup()} to abort a blocking operation
516    * (in which case, {@link InterruptException} will be raised), we discourage their use since they may cause a clean
517    * shutdown of the consumer to be aborted. Interrupts are mainly supported for those cases where using {@link #wakeup()}
518    * is impossible, e.g. when a consumer thread is managed by code that is unaware of the Kafka client.
519    *
520    * <p>
521    * We have intentionally avoided implementing a particular threading model for processing. This leaves several
522    * options for implementing multi-threaded processing of records.
523    *
524    * <h4>1. One Consumer Per Thread</h4>
525    *
526    * A simple option is to give each thread its own consumer instance. Here are the pros and cons of this approach:
527    * <ul>
528    * <li><b>PRO</b>: It is the easiest to implement
529    * <li><b>PRO</b>: It is often the fastest as no inter-thread co-ordination is needed
530    * <li><b>PRO</b>: It makes in-order processing on a per-partition basis very easy to implement (each thread just
531    * processes messages in the order it receives them).
532    * <li><b>CON</b>: More consumers means more TCP connections to the cluster (one per thread). In general Kafka handles
533    * connections very efficiently so this is generally a small cost.
534    * <li><b>CON</b>: Multiple consumers means more requests being sent to the server and slightly less batching of data
535    * which can cause some drop in I/O throughput.
536    * <li><b>CON</b>: The number of total threads across all processes will be limited by the total number of partitions.
537    * </ul>
538    *
539    * <h4>2. Decouple Consumption and Processing</h4>
540    *
541    * Another alternative is to have one or more consumer threads that do all data consumption and hands off
542    * {@link ConsumerRecords} instances to a blocking queue consumed by a pool of processor threads that actually handle
543    * the record processing.
544    *
545    * This option likewise has pros and cons:
546    * <ul>
547    * <li><b>PRO</b>: This option allows independently scaling the number of consumers and processors. This makes it
548    * possible to have a single consumer that feeds many processor threads, avoiding any limitation on partitions.
549    * <li><b>CON</b>: Guaranteeing order across the processors requires particular care as the threads will execute
550    * independently an earlier chunk of data may actually be processed after a later chunk of data just due to the luck of
551    * thread execution timing. For processing that has no ordering requirements this is not a problem.
552    * <li><b>CON</b>: Manually committing the position becomes harder as it requires that all threads co-ordinate to ensure
553    * that processing is complete for that partition.
554    * </ul>
555    *
556    * There are many possible variations on this approach. For example each processor thread can have its own queue, and

920       /**

923        * assignment (if there is one).</b> Note that it is not possible to combine topic subscription with group management
924        * with manual partition assignment through {@link #assign(Collection)}.

927        *
928        * <p>

930        * group and will trigger a rebalance operation if any one of the following events are triggered:
931        * <ul>
932        * <li>Number of partitions change for any of the subscribed topics
933        * <li>A subscribed topic is created or deleted
934        * <li>An existing member of the consumer group is shutdown or fails
935        * <li>A new member is added to the consumer group
936        * </ul>
937        * <p>
